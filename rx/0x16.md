The server asks for a ping. The client answers immediately with a [PING_REPLY (0x15)](./15-ping-reply)
that carries a timestamp, a hash of the request's `itemID`, and several values the server gave it earlier
(state bits, reach, physics values), plus two values the client measures itself: the most jumps you made
in the air, and the code of the last failed integrity check. That lets the server measure the round trip,
check that the client still uses the values it was sent, and notice a tampered client.

| Field | Used as |
|---|---|
| `itemID` | a challenge: the reply's `targetNetID` is a hash of this number written as decimal text |

Nothing else in the request is read.

The hash (`0x1e69d5c`, proton's `HashString`), to check a reply on the server:

```cpp
uint32_t hash_string(const char *s) {
    uint32_t h = 0x55555555;
    for (; *s; ++s) h = ((h >> 27) | (h << 5)) + (uint8_t)*s;
    return h;
}
// expected reply.targetNetID == hash_string(std::to_string(request_itemID).c_str())
```

### The reply the client builds

All fields not listed are 0. No extra data; sent reliable.

| Reply field | Value |
|---|---|
| `type` | 0x15 |
| `jumpCount` (byte 2) | the most jumps you have made without landing since you spawned (avatar+0xcc, low byte; see below) |
| `buildRange` (byte 3) | the code of the last integrity check that failed (avatar+0x258), only if ≥ 1; 0 = none failed |
| `netID` | your state bits: the `itemID` of the last [0x14](./14-set-character-state) for you |
| `targetNetID` | `HashString(to_string(request.itemID))` (proton's string hash, `0x1e69d5c`) |
| `itemID` | the client's tick count in ms |
| `posX` | your Fist reach in pixels: (byte 3 of the last 0x14 − 0x80 + 2) × 32 |
| `posY` | your reach for other items in pixels: (byte 2 of the last 0x14 − 0x80 + 2) × 32 |
| `speedX` | the `speedY` value of the last 0x14 for you |
| `speedY` | the `speedX` value of the last 0x14 for you |

**Jump count (byte 2).** The jump code (`0x13045d4`) adds 1 to avatar+0xc0 for each jump that starts in the
air, unless you wear an item that allows extra jumps or you jump off a block that resets it. When you land
(`0x12f9fd0`), avatar+0xcc becomes the larger of itself and avatar+0xc0, and +0xc0 goes back to 0. avatar+0xcc
is only reset when the avatar is created ([OnSpawn](/functions/OnSpawn)), so this is the record for the
current world visit.

**Integrity code (byte 3).** The client checks itself in several places (the physics code, `OnSetPos`, ...).
For example, it compares a sum of its scrambled physics constants with a copy kept elsewhere. When a check
fails, it stores a code from 1 to 28 at avatar+0x258 (the code says which check failed). It also sends
[APP_INTEGRITY_FAIL (0x19)](./19-app-integrity-fail) with the same code at most once per cooldown. The code
stays set, so every later ping reply repeats it.

The avatar fields are only filled while you have an avatar in a world; otherwise `type`, `targetNetID`,
`itemID`, `posX` and `posY` are set.

### Decompiled handler

```c
case 0x16: {
    packet r = {0};
    r.type   = 0x15;
    r.itemID = GetTick();
    r.posX   = (self->fistRange  + 2) * 32.0f;               // self+0x2f4 (0x1373de8)
    r.posY   = (self->buildRange + 2) * 32.0f;               // self+0x2f8 (0x1373e00)
    r.targetNetID = HashString(to_string(pkt->itemID).c_str(), 0);
    NetAvatar *me = self->localPlayer;
    if (me) {
        if (me->integrityFail > 0) r.buildRange = (u8)me->integrityFail;   // avatar+0x258
        r.netID     = me->stateBits;                          // avatar+0x170
        r.jumpCount = (u8)me->maxAirJumps;                    // avatar+0xcc
        r.speedX    = Unscramble(me->phys.speedY);            // avatar+0x1b4 - avatar+0x1c0 / 2
        r.speedY    = Unscramble(me->phys.speedX);            // avatar+0x1d4 - avatar+0x1e0 / 2
    }
    SendPacket(4, &r, 56, NULL, GetApp()->client->peer, 1);   // 0x157ee8c
}
```

<small>Handler: `0x1374a98` (switch case) in the 5.60 arm64 client; callees read: `0x1e69d5c`, `0xe1f798`, `0x157ee8c`; field writers `0x13045d4`, `0x12f9fd0`, `0x137c374`. The same reply is also built by `0x1373be4`, which the small network pump `0x1142f34` uses during ads (see below).</small>

### What the client sends

The client also sends 0x16 itself, with every field 0 (reliable, no extra data). It isn't a ping the server
must answer in kind: the client uses it to get *any* packet back. Both senders (`0x137c2a4`, `0x1382d30`) also
start the client's "waiting for the server" timer (GameLogic+0x2ec) if it isn't running.

That timer is set by several actions (for example punching, `0x137c33c`) and cleared when a game packet
arrives (at the start of the packet handler `0x1373e20`; some function handlers such as
[OnTalkBubble](/functions/OnTalkBubble) clear it too). While it runs, the update loop (`0x136a80c`) shows a waiting indicator after 500 ms
(`0x135cdc8`), and after 30 s with no packet logs "DISCONNECTED: Timeout exceeded" and reconnects (`0x11433d4`),
unless the store or another screen is open.

When it's sent:

| Sender | When |
|---|---|
| `0x137c2a4` | the app comes back to the foreground (`0x10841c8`, "APP_STATE OnEnterForeground!") while connected and before a deadline (app+0xbdc); after the deadline the client reconnects instead. Also from the ad SDK (probably while a full-screen ad plays): the Java side calls `IronSourceManager.sendPingToServer`, whose native lambda (`0x1f29028`) sends the 0x16 and then runs a small network pump (`0x1142f34`) that only handles 0x16 and 0x00 (`0x1373be4`), to keep the connection alive |
| `0x1382d30` | after an in-app purchase result (`0x16dc6d4`, "type\|NORMAL", and the delayed-purchase path `0x1d92468`, "type\|DELAYED"). It also sets GameLogic+0x2fc; the next packet from the server then makes the client send its pending purchase receipt (`action\|chaching`, `0x1083db8`) |

So a server should answer a 0x16 from the client with some packet (a 0x16 back works: the client replies with
0x15); a client that hears nothing for 30 s while waiting reconnects.

<small>Senders: `0x137c2a4`, `0x1382d30`; timer users `0x137c33c`, `0x136a80c`, `0x1373be4`.</small>
